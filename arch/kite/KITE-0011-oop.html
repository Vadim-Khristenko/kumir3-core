1. Текущее состояние

Честно AST-модель ООП богатая (классы, структуры, интерфейсы, типажи, impl, generics, модификаторы виртуальный/переопределить/финал/абстрактный, видимость). Уже сделано: идентичность объектов (стабильный type_id через TypeRegistry) и разрешение методов по иерархии с работающим переопределением (полиморфизм), а также проверка видимости полей (инкапсуляция) и исполнение тел конструкторов. Осталось: дефолтные реализации типажей и проверка соответствия интерфейсу, статические члены, свойства-аксессоры, деструкторы и цепочка конструкторов к предку, generics, перегрузка операторов.

Ниже: ✅ — работает, 🧪 — частично/в AST, 📋 — спроектировано.

2. Модель типов

ВидНазначениеДоступность
классКласс с наследованием, методами, виртуальной диспетчеризацией.🧪
структураЛёгкие данные без виртуальной диспетчеризации.🧪
интерфейсТолько сигнатуры методов.🧪
свойство (trait)Типаж с дефолтными реализациями.🧪
перечисление (enum)Перечисление с вариантами. Литерал варианта Перечисление::Вариант и вариант с данными Перечисление::Вариант(x) вычисляются — они разрешаются тем же путём, что и члены модуля (KITE 15); раньше это была ошибка «не реализовано».✅
@nativeНативный тип из ядра/расширения. Механизм фабрик в реестре типов существует, но ни одна фабрика не зарегистрирована, и нативный объект из кода Кумира создать нечем; нативные функции — отдельный, работающий механизм (см. KITE 16).📋

Член типа описывается полем (Field), методом (Method), конструктором/деструктором; у каждого — видимость и модификаторы.

3. Наследование и полиморфизм

  • Наследование: расширяет (один предок), реализует (интерфейсы).
  • Разрешение методов по иерархии: поиск метода идёт от класса объекта вверх по предкам — первый найденный выигрывает (vtable-подобно). ✅
  • Виртуальная диспетчеризация: вызов по фактическому типу (переопределение выигрывает); финал запрещает переопределение, абстрактный требует реализации в неабстрактном потомке. ✅
  • Вызов предка: предок.метод(...) — вызов реализации родителя (обходит переопределение); поиск начинается с родителя класса, где определён текущий метод. ✅
  • Абстрактные классы: создание экземпляра абстрактного класса запрещено. ✅
Нормативно: предок — только в позиции вызова предок допустим исключительно в форме предок.метод(…). Голый предок (как значение, приёмник поля или аргумент) — явная ошибка выполнения: «'предок' можно использовать только как вызов метода предка: 'предок.метод(...)' — самостоятельным значением он не является». Это не «не реализовано», а нормативный запрет: объект Кумира — единая плоская запись полей, отдельного объекта-предка в модели не существует. Синтаксис предок(…) для цепочки конструкторов пока не поддержан (§5). Грамматика этих форм — KITE 12.
Фундамент — идентичность объектов Корректная диспетчеризация требует надёжной связи объект → класс (через TypeId и TypeRegistry), а не сопоставления по набору полей. Это первый шаг плана (§9).

4. Интерфейсы и типажи

  • Интерфейс — набор сигнатур; тип обязан их реализовать.
  • Типаж (свойство) — как интерфейс, но с дефолтными реализациями методов и супертипажами.
  • Реализация: реализация Типаж для Тип привязывает методы к типу.
  • Диспетчеризация через impl-блоки: метод из реализация [Типаж] для Тип ищется по типу и предкам после методов класса. ✅
  • Дефолтные реализации типажа и проверка соответствия интерфейсу — на очереди. 📋
  • Проверка реализации через TypeRegistry (номинальный подтип, см. KITE 10). 🧪

5. Поля, свойства, инкапсуляция

ВозможностьОписаниеДоступность
Видимостьоткрытый/закрытый/защищённый — доступ к полю извне класса проверяется (закрытое — только владелец, защищённое — владелец и потомки).✅
Типизация полейЗначение по умолчанию для поля уже берётся из default_value движка (KITE 10) ✅; проверка типа при записи в поле — ещё нет.📋
Свойства-аксессорыВычисляемые чтение/запись (get/set) поверх полей.📋
Статические членыПоля/методы уровня типа (статический): модификатор разбирается и хранится в AST, но интерпретатор его не учитывает.🧪
Изменяемостьизмен/конст для полей.📋
КонструкторКонструктор исполняется: подбор по числу аргументов, собственный кадр вызова, исполнение тела, изменения через это попадают в созданный объект; ошибка в теле конструктора — это ошибка выражения новый (не глотается, см. KITE 14).✅
ДеструкторРазбирается и хранится в ClassDef, но не исполняется. Объявление деструктор порождает предупреждение в момент определения класса, называющее класс: «деструктор класса 'Имя' объявлен, но не будет исполнен: детерминированная точка разрушения объекта не определена (KITE-0011); освобождайте ресурсы явным методом». Причина: Value::Object — значение с семантикой копирования, без идентичности экземпляра и без момента «последнего владельца». Контракт закреплён тестом.🧪
Цепочка предок(…)Явный вызов конструктора предка: синтаксиса нет.📋

Порядок построения объекта сегодня: поля получают значения по умолчанию (default_value или явный инициализатор поля) → вычисляются аргументы в кадре вызывающего (KITE 4) → создаётся кадр конструктора с это → исполняется тело → объект берётся из это.

6. Обобщённые типы

  • Параметры типа (type_params) на классах, методах, интерфейсах и типажах.
  • Ограничения где — требования к параметрам (реализует типаж, подтип и т.п.).
  • Представление через TypeKind::Generic { name, type_args }; проверка совместимости — движком (ковариантно по аргументам).
  • Стратегия: стирание с проверкой типов на границах (мономорфизация — позже). 📋

7. Перегрузка операторов

  • Операторы выражаются типажами-операторами (напр. Сложение, Сравнение); a + b разворачивается в вызов метода типажа.
  • Тип результата операции даёт движок (result_of_binop) либо сигнатура метода типажа.
  • Это позволяет дробь, комплекс, вектор и т.п. вести себя как числа. 📋

8. Связь с движком типов

ООП опирается на единый движок (KITE 10):

  • Номинальный подтип (nominal-правило) — наследование и реализация интерфейсов через TypeRegistry.
  • Проверка присваиваний и параметров методов — check_assignable.
  • Типы полей и значения по умолчанию — default_value.
  • Перегрузка операторов — типизация через result_of_binop.

9. План реализации

  1. ✅ Идентичность объектов: класс регистрируется в TypeRegistry при объявлении; объект несёт стабильный type_id (вместо сопоставления по полям).
  2. ✅ Разрешение методов по иерархии: поиск метода от класса объекта вверх по предкам; переопределение подкласса выигрывает (полиморфизм).
  3. ✅ Виртуальная диспетчеризация: переопределение, предок.метод(), запрет инстанцирования абстрактный, запрет переопределения финал, обязательность реализации абстрактных методов.
  4. 🚧 Типажи и интерфейсы: диспетчеризация в impl-методы — ✅; дефолтные реализации типажа и проверка соответствия интерфейсу — далее.
  5. 🚧 Инкапсуляция и свойства: проверка видимости полей — ✅; свойства-аксессоры и проверка типа при записи в поле — далее.
  6. 🚧 Жизненный цикл объекта: исполнение тел конструкторов и проброс их ошибок — ✅; объявление деструктора предупреждает, что он не будет исполнен — ✅; собственно исполнение деструкторов (требует модели владения вместо копирования), цепочка предок(…) и статические члены — далее.
  7. Обобщённые типы: параметры и ограничения где.
  8. Перегрузка операторов: типажи-операторы.
