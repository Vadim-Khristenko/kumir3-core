1. Мотивация и цели

Kumir 3 — учебный язык, и его тесты обязаны быть учебными материалами, а не только страховкой от регрессий. На момент написания документа во всём репозитории — лишь 7 файлов .kum (четыре в examples/), и ни один не проверяется автоматически. Это крупнейший технический и педагогический долг проекта.

Документ решает три задачи одновременно:

Регрессии

Каждая программа корпуса — это golden-тест: если рефакторинг меняет её вывод, тест краснеет. Корпус — это сеть безопасности под всеми фазами эволюции языка.

Спецификация в действии

Программа с ожидаемым выводом — исполнимое доказательство того, что фича из KITE работает именно так, как написано. Корпус — conformance-набор языка.

Учебник

Программы снабжены комментариями-объяснениями и разложены по уровням сложности — ученик читает корпус как задачник с решениями.

Целевые объёмы (из мастер-плана) 100+ программ к концу первой волны кода (Волна 2), 500+ программ к концу года. Тестовая планка ядра: с текущих 455 #[test] → 700+ юнитов + 100 golden-программ.

2. Слои тестирования

Тестирование Kumir 3 многослойно. Настоящий документ нормирует прежде всего слой 3 (golden-корпус); слои 1–2 уже существуют и описаны здесь кратко ради полноты картины.

СлойЧто проверяетГде живётСтатус
1. Юнит-тесты ядра Отдельные функции лексера/парсера/интерпретатора по BetterDoc (Arrange / Act / Assert). Со-локация #[cfg(test)] mod tests в модулях shared/, interpreter/, compiler/. ✅
2. Характеризационные тесты Фиксируют фактическое поведение (в т.ч. причуды), чтобы изменения были осознанными. interpreter/src/interpreter/typeops_characterization.rs (38 тестов), shared/tests/constants_characterization.rs. ✅
3. Golden-корпус программ Целые программы .kum с встроенным ожидаемым выводом; сквозная проверка «исходник → вывод». examples/corpus/ + раннер в тестах интерпретатора. 📋
4. Эталон совместимости КуМир 2 Программы из школьных задачников КуМир 2, обязанные исполняться бит-в-бит. Подкаталог корпуса (уровень 1); связан с KITE 6. 📋
Характеризация ≠ golden Характеризационный тест закрепляет то, что есть (даже баг), чтобы поймать непреднамеренное изменение. Golden-программа закрепляет то, что должно быть по спецификации. Когда фиксируется баг из характеризации — соответствующий тест обновляется осознанно, со ссылкой на нормативный KITE (напр. KITE 13 для семантики операций).

3. Golden-формат тест-кейса

Формат основан на конвенции KITE 9 §3 (| КЕЙС: … / | ОЖИДАЕМЫЙ ВЫВОД: …) и доводит её до нормативной, машинно-проверяемой формы. Ключевое свойство: кейс живёт в комментариях самой программы — файл остаётся валидной программой Kumir 3, которую можно запустить руками, и одновременно — самопроверяемым тестом.

Кейс — это блок директив-комментариев. Директива начинается с символа комментария |, за которым следуют пробел, ключевое слово в верхнем регистре и двоеточие.

3.1 Минимальный однокейсовый файл

| КЕЙС: НОД(48, 36)
| ОЖИДАЕМЫЙ ВЫВОД:
| 12

алг цел нод(цел a, цел b)
нач
  нц пока b ≠ 0
    цел t := b
    b := a мод b
    a := t
  кц
  знач := a
кон

алг главный
нач
  вывод нод(48, 36)
кон

Раннер собирает ожидаемый вывод из строк директивы | ОЖИДАЕМЫЙ ВЫВОД: (см. §4 про многострочность), исполняет программу и сравнивает захваченный вывод с ожидаемым.

3.2 Многокейсовый файл

Один файл может содержать несколько кейсов. Каждый новый заголовок | КЕЙС: открывает новый кейс; предыдущий закрывается. Все директивы до первого | КЕЙС: — файловые (глобальные) настройки, применяемые ко всем кейсам файла.

| ФАЙЛ: примеры факториала            <— заголовок файла (необязателен)
| АВТОР: корпус Kumir 3
| УРОВЕНЬ: 1

алг цел факт(цел n)
нач
  если n ≤ 1 то знач := 1 иначе знач := n * факт(n - 1) все
кон

| КЕЙС: факт(0)
| ВВОД:
| ОЖИДАЕМЫЙ ВЫВОД:
| 1
алг главный нач вывод факт(0) кон

| КЕЙС: факт(5)
| ОЖИДАЕМЫЙ ВЫВОД:
| 120
алг главный нач вывод факт(5) кон
Одна точка входа на кейс Каждый кейс исполняется как самостоятельная программа: код кейса конкатенируется с общей «прелюдией» файла (объявлениями до первого | КЕЙС:). В пределах одного кейса должна быть ровно одна точка входа алг главный (либо единственный безымянный алг — по правилам запуска KITE 9 §2). Общие вспомогательные алгоритмы выносятся в прелюдию.

4. Грамматика заголовков кейса

Директивы кейса нормируются следующей грамматикой (EBNF, согласована со стилем KITE 12):

директива      = "|" пробел ключ ":" [ пробел значение ] перевод_строки ;
блок           = "|" пробел значение перевод_строки ;   (* строка продолжения *)

ключ           = "ФАЙЛ" | "АВТОР" | "УРОВЕНЬ" | "КАТЕГОРИЯ" | "ТЕГИ"
               | "КЕЙС" | "ВВОД" | "АРГУМЕНТЫ" | "ОЖИДАЕМЫЙ ВЫВОД"
               | "ОЖИДАЕМАЯ ОШИБКА" | "КОД ВОЗВРАТА" | "ДОПУСК"
               | "ТАЙМАУТ" | "ПРОПУСТИТЬ" | "ТОЛЬКО" ;

кейс           = "| КЕЙС:" описание перевод_строки
                 { продолжение_директивы }
                 код_программы ;
продолжение_директивы = директива | блок ;

Нормативные ключи:

4.1 Многострочные значения

Значение директивы продолжается строками-блоками вида | текст (палка, пробел, текст без ключа-двоеточия), идущими сразу за директивой. Пустая строка блока пишется как «палка + пробел + ничего». Первый пробел после | — разделитель и в вывод не входит; остальные пробелы значимы.

| ОЖИДАЕМЫЙ ВЫВОД:
| Привет, мир!
|
| Строка 3 с ведущими пробелами:    хвост
Почему в комментариях Символ | — комментарий Kumir 3 (KITE 12): весь блок кейса невидим для интерпретатора, файл остаётся исполнимой программой. Раннеру нужен лишь текстовый предпарсер комментариев — он не зависит от парсера языка и работает даже на программах, которые пока не исполняются.

5. Правила сравнения и допуски

По умолчанию сравнение — точное посимвольное после единственной нормализации: перевод строки приводится к \n (CRLF→LF), финальный перевод строки не учитывается. Директива | ДОПУСК: ослабляет сравнение по режимам:

РежимЧто делаетКогда
точноПобайтовое равенство (после нормализации переводов строк). По умолчанию.Детерминированный текстовый вывод.
пробелыСхлопывает подряд идущие пробелы/табы в один, обрезает хвостовые пробелы строк.Форматирование таблиц, выравнивание.
вещ:<eps>Числа сравниваются с абсолютным/относительным допуском eps (напр. вещ:1e-9); нечисловой текст — точно.Вещественные вычисления, где важен смысл, а не 15-я цифра.
регэкспЭталон — регулярное выражение; вывод должен совпасть целиком.Вывод с недетерминированным фрагментом (время, адрес).
Детерминизм — по умолчанию Программа корпуса обязана быть детерминированной: один и тот же исходник в одном окружении даёт один и тот же вывод (принцип KITE 9 §9; для async — требование однопоточного детерминизма KITE 3 §8). Допуски вещ/регэксп — исключение для честно недетерминированных мест, а не костыль от флаки-тестов. Недетерминированный без допуска кейс — ошибка автора.

При расхождении раннер печатает унифицированный diff (ожидание vs факт), имя файла, номер и описание кейса — по духу «сообщение читает ученик» (KITE 8).

6. Ожидаемые ошибки

Кейс может проверять, что программа должна завершиться ошибкой (обучение чтению ошибок — KITE 9 §4). Тогда вместо ОЖИДАЕМЫЙ ВЫВОД используется ОЖИДАЕМАЯ ОШИБКА.

| КЕЙС: деление на ноль
| ОЖИДАЕМАЯ ОШИБКА: DivisionByZero
| ОЖИДАЕМЫЙ ВЫВОД:
| до деления
алг главный
нач
  вывод "до деления", нс
  вывод 1 / 0
кон

Нормативные правила:

  • Значение ОЖИДАЕМАЯ ОШИБКА — вид ошибки из перечня RuntimeErrorKind (см. KITE 14; 13 видов в interpreter/src/interpreter/error.rs), опционально с подстрокой сообщения после /: | ОЖИДАЕМАЯ ОШИБКА: TypeMismatch / ожидался цел.
  • Сравнение вида ошибки — точное по имени; сравнение сообщения — содержит подстроку (устойчиво к переформулировкам).
  • ОЖИДАЕМЫЙ ВЫВОД рядом с ОЖИДАЕМАЯ ОШИБКА задаёт вывод до момента падения (частичный вывод обязан совпасть).
  • Если программа завершилась успешно, а ждали ошибку (или наоборот) — кейс красный.
Связь с моделью ошибок Перечень видов ошибок и формат сообщений нормирует KITE 14. Пока он в разработке, раннер опирается на фактические RuntimeErrorKind. Расхождение имён между корпусом и KITE 14 после его принятия — баг корпуса.

Уровни повторяют «одну образовательную дугу» Kumir 3 (KITE 1 §3): один язык от 5-го класса до студента.

Правда о доступности фич Корпус проверяет реально исполнимое. Программа уровня 5, опирающаяся на пока-неисполнимую фичу (?-пропагация, T!E, настоящий async — см. аудит правды), помечается | ПРОПУСТИТЬ: KITE-0014 и активируется, когда фича появится. Так корпус растёт вместе с языком, не давая ложно-зелёных или вечно-красных тестов.

9. Именование и требования к программе-примеру

  • Имя файла — латиница-транслит, kebab-case, суффикс .kum (напр. prostye-chisla.kum): дружественно к git и кроссплатформенно.
  • Заголовок-комментарий: первая строка файла — краткое описание задачи по-русски.
  • Объяснения: программа корпуса — учебник, значит содержит комментарии, объясняющие почему, а не только что (KITE 8).
  • Стиль: код соответствует стайл-гайду; новые конструкции (?., лямбды, диапазоны с шагом) — там, где они проясняют, а не затемняют.
  • Самодостаточность: программа не читает сеть/часы без допуска-регэкспа и не зависит от внешних файлов вне своего каталога кейса.
  • Один смысл на файл: файл иллюстрирует одну идею; вариации — соседние кейсы того же файла.

10. Golden-раннер 📋 Предложено

Раннер (к постройке в Волне 2) — тестовый харнес в крейте интерпретатора. Алгоритм:

  1. Обход: рекурсивно найти все examples/corpus/**/*.kum.
  2. Предпарсинг: текстовым сканером извлечь блоки кейсов из комментариев | по грамматике §4 (не задействуя парсер языка).
  3. Сборка кейса: прелюдия файла + код кейса → исходник одной программы.
  4. Исполнение: запустить через интерпретатор, подав ВВОД на stdin, захватив вывод (через будущий поток памяти STDIO — KITE 7 §10, не глобальный буфер), с ТАЙМАУТ.
  5. Сравнение: применить режим ДОПУСК (§5) или проверку ошибки (§6).
  6. Отчёт: при провале — diff, путь, кейс; счётчики pass/fail/skip.

Точка интеграции — обычный cargo test: харнес порождает по под-тесту на кейс, так что корпус запускается той же командой, что и юниты, и виден в CI.

// Набросок харнеса (interpreter/tests/golden.rs) — ПРЕДЛОЖЕНО.
#[test]
fn golden_corpus() {
    let mut report = GoldenReport::default();
    for file in discover("examples/corpus") {          // 1. обход
        let doc = parse_cases(&file);                   // 2. предпарсинг директив
        for case in doc.cases {
            if case.skip.is_some() { report.skip(&case); continue; }
            let src = doc.prelude.clone() + &case.code; // 3. сборка
            let got = run(&src, &case.input, case.timeout); // 4. исполнение
            match compare(&case.expected, &got) {        // 5. сравнение
                Ok(())   => report.pass(&case),
                Err(diff) => report.fail(&case, diff),   // 6. отчёт (diff)
            }
        }
    }
    report.assert_all_green();
}
Обновление эталонов Переменная окружения KUMIR_GOLDEN=bless перезаписывает | ОЖИДАЕМЫЙ ВЫВОД: фактическим выводом (для осознанного массового обновления эталонов при намеренной смене поведения). По умолчанию раннок только сверяет и никогда не пишет.

11. Интеграция с CI и метрики

  • Зелёный корпус — условие мержа: любой упавший кейс блокирует CI, как обычный тест.
  • Покрытие как метрика: доля фич языка, у которых есть хотя бы один golden-кейс; растёт от волны к волне (цель — каждая ✅-фича KITE покрыта корпусом).
  • Счётчик объёма: число программ по уровням — публичный индикатор прогресса (100+ → Волна 2, 500+ → год).
  • Эталон КуМир-2: подкаталог kumir2-etalon/ — приёмочный критерий режима совместимости (бит-в-бит; KITE 6).
