Что нормативизирует этот документ KITE 15 фиксирует фактическое поведение резолюции модулей и импортов, как оно реализовано в интерпретаторе, а не идеализированную модель. Всё, что помечено 📋, ещё не работает и описывает целевую семантику. Каталог встроенных библиотек и формы использовать для них — предмет KITE 5; здесь описан общий механизм модулей, пространств имён и резолюции, частью которого библиотеки являются.

1. Обзор и цель

В Kumir 3 модуль — это единица кода, из которой другой код может брать алгоритмы и классы. Модулем может быть:

  • отдельный файл .kum (файловый модуль, как в Python);
  • директория-проект с манифестом kumir.toml (модуль-проект);
  • встроенная библиотека ядра (время, система, файлы, сеть);
  • пользовательская библиотека (директория или файл, загружаемая как библиотека);
  • именованный блок модуль … кон внутри одного файла.

Все формы вводятся двумя взаимозаменяемыми ключевыми словами — использовать и подключить. Они не различаются семантически: конкретный вид импорта определяет резолвер по форме пути, а не по ключевому слову.

Одно правило вместо многих Форму импорта выбирает не автор программы явным синтаксисом, а резолвер — по тому, как выглядит путь: строка с .kum или разделителем каталогов → файл; каталог с kumir.toml → проект; простое имя → библиотека. Это единый вход и предсказуемая цепочка проверок (раздел 3).

2. Формы импорта

Синтаксис объявления импорта (парсится в Stmt::Import { path, alias, items }): 

использовать <путь> [: имя1, имя2, …] [как Алиас]
подключить  <путь> [: имя1, имя2, …] [как Алиас]

<путь> — это строковый литерал ("./математика.kum") или идентификатор (время, сеть). Обе записи допустимы.

ПримерЧто импортируетсяДоступность
использовать времяВстроенная библиотека по имени.✅
использовать время как тБиблиотека под алиасом т.✅
использовать время@^2.0Библиотека с указанием версии (SemVer, только для библиотек).🧪
подключить "./математика.kum"Соседний файл .kum по относительному пути.✅
подключить "./математика.kum" как матФайловый модуль под алиасом мат.✅
подключить "../общее/утилиты"Файл без расширения; резолвер добавит .kum.✅
использовать "./библиотека"Директория-проект с kumir.toml — импорт её главного файла.✅
использовать время: время_мс, паузаВыборочный импорт (список имён после :).🧪
Разделитель списка выборочного импорта — двоеточие Парсер принимает использовать Модуль: имя1, имя2 (Token::Colon), а не фигурные скобки. Записи вида использовать время { now_ms } из старых примеров не парсятся; правильная форма — через :. Внутренние комментарии в коде, упоминающие { … }, отражают устаревший замысел.

3. Алгоритм резолюции

Инструкция импорта разрешается процедурой process_import (interpreter/src/interpreter/import.rs). Резолвер проверяет форму пути в строго фиксированном порядке и берёт первое сработавшее правило:

№ПроверкаЧто делает
1 Директория-проект. Путь (как есть или относительно базовой директории) — существующая директория, содержащая kumir.toml. Резолвится главный файл проекта (см. ниже), импортируется как модуль: его публичные алгоритмы и классы становятся вызываемыми.
2 Файл .kum. Путь оканчивается на .kum, начинается с ./ или ../, либо содержит / или \. Импортируется как файловый модуль через FileImporter.
3 Пользовательская библиотека. Путь — существующая директория, либо содержит разделитель каталогов, но не подошёл под п. 1–2. Загружается как библиотека через LibraryManager (директория с kumir.toml → как библиотека-проект, иначе как файл).
4 Встроенная библиотека. Простое имя, которое resolve_import_path распознаёт как известную библиотеку (по ru/en-имени или алиасу). Загружается библиотека ядра из реестра.
5 Иначе Ошибка: «Модуль или библиотека '<путь>' не найдены».

3.1 Разрешение пути файлового модуля

Для файловых модулей (FileImporter::resolve_path) действует такой порядок:

  • Относительный путь (./, ../) — присоединяется к базовой директории;
  • Абсолютный путь — берётся как есть;
  • Простое имя — ищется по всем директориям поиска (по умолчанию — базовая директория); дополнительно проверяется вариант «директория с index.kum».

Расширение .kum подставляется автоматически, если его нет (ensure_kum_extension): сперва пробуется <путь>.kum, затем файл без расширения.

Базовая директория Для запуска файла базовой директорией становится каталог этого файла (CLI и TUI вызывают set_base_dir). Поэтому относительные импорты разрешаются относительно расположения импортирующего файла, а не текущего каталога процесса. Базовая директория всегда входит в список директорий поиска.

3.2 Главный файл проекта

Для директории-проекта (п. 1) главный файл выбирается так (resolve_dir_library_main):

  1. если kumir.toml задаёт главный файл ([build] main или [project]/[package] main) и он существует — берётся он;
  2. иначе перебираются запасные общепринятые расположения в порядке: src/lib.kum → lib.kum → src/main.kum → main.kum;
  3. первый существующий файл и есть главный.

4. Регистрация имён и пространства имён

После загрузки модуля его публичные имена регистрируются в среде исполнения. Пространство имён модуля — это префикс с точкой (Алиас.имя или ИмяМодуля.имя), а не отдельная область.

Что импортировалиКак зарегистрированы алгоритмы
С алиасом … как Алиас Только под именем Алиас.имя (пространство имён обязательно).
Без алиаса И под именем ИмяМодуля.имя, и под коротким имя (импорт «вливается» в текущее пространство).
Выборочный : имя1, имя2 Каждое перечисленное имя регистрируется как Префикс.имя; классы — под своим коротким именем.

Имя модуля по умолчанию — имя файла без расширения (или алиас, если задан). Классы импортированного модуля всегда регистрируются под своим коротким именем (в текущей реализации пространство имён на классы не навешивается, кроме случая директории-проекта без алиаса).

Разные пути регистрации модулей В коде существуют две почти совпадающие процедуры регистрации — register_imported_module (для директории-проекта) и execute_file_import (для файлового модуля через executor). Они дают одинаковый результат «префикс с точкой», но детали (навешивание префикса на класс) различаются. Это дубликат логики — кандидат на унификацию; нормативно следует считать эталоном правило «Префикс.имя для алгоритмов, короткое имя для классов».

5. Доступ к членам модуля

Kumir 3 синтаксически различает два оператора доступа к члену. Обе формы исполняются и приводятся к одному и тому же разрешению имени:

ФормаКак парситсяКак исполняетсяДоступность
Алиас.функция(…)
точка		 Постфиксный . + ( → Expr::Call("Алиас.функция", …) — точка становится частью имени. Ищется алгоритм с полным именем Алиас.функция, зарегистрированный при импорте. Работает. ✅
Модуль::член
двойное двоеточие		 Постфиксный :: → Expr::ModuleAccess("Модуль", "член"); вызов Модуль::функция(…) → Expr::Call("Модуль::функция", …). Обе формы приводятся к точечному полному имени Модуль.член и разрешаются так же, как точечная запись (evaluator/module.rs). Работает. ✅ 
подключить "./математика.kum" как мат

алг Тест
нач
    вывод мат.квадрат(5)   | ✅ работает: вызов алгоритма "мат.квадрат"
    вывод мат::квадрат(5)  | ✅ работает: то же имя "мат.квадрат"
кон
Нормативно: . и :: — равноправные разделители Обе записи — Модуль.член и Модуль::член — обращаются к одному и тому же члену: :: нормализуется в точечное полное имя Модуль.член, под которым импорт и объявление модуль … кон регистрируют алгоритмы. Порядок разрешения Модуль::член в позиции значения: вариант перечисления → переменная модуля под полным именем → алгоритм модуля (ясная ошибка с подсказкой вызвать его) → ошибка «член не найден», называющая и модуль, и член. Для вызова Модуль::член(…): алгоритм → вариант перечисления с данными → функция загруженной библиотеки. Тем же путём впервые заработали литералы вариантов перечисления Перечисление::Вариант — ранее они уходили в ту же ветку «не реализовано».

Для библиотек вызов идёт через отдельный путь: функции регистрируются под полным именем библиотека::функция и под короткими алиасами, а квалифицированный вызов обслуживает call_qualified_function. Детали вызова библиотечных функций — в KITE 5.

6. Модули и экспорт: модуль / экспорт

6.1 Видимость по умолчанию

Если в файле нет инструкции экспорт, публичны все его алгоритмы и классы (is_exported возвращает истину при отсутствии явного списка). Инструкция экспорт имя1, имя2, … в глобальной области файла ограничивает публичный набор перечисленными именами: экспортируется только то, что в списке. 

экспорт квадрат, куб      | только эти два алгоритма видны при импорте

алг цел квадрат(цел x) нач знач := x * x кон
алг цел куб(цел x)    нач знач := x * x * x кон
алг цел приватный(цел x) нач знач := x кон   | не экспортирован → не виден извне
Ключевое слово экспорт и алиас pub Лексема экспорт имеет английские алиасы export и pub (shared/build.rs). В файловом модуле она задаёт список публичных имён; как модификатор отдельного объявления (pub алг …) она в текущей резолюции не участвует — фильтрация идёт по единому списку экспорт.

6.2 Именованные модули модуль … кон

Внутри одного файла можно объявить именованный модуль (парсится в Stmt::ModuleDecl): 

модуль Гео
    алг вещ площадь(вещ a, вещ b) нач знач := a * b кон
кон

алг Главный
нач
    вывод Гео.площадь(3, 4)   | ✅ 12
кон

При исполнении execute_module_decl регистрирует каждый алгоритм модуля дважды: под полным именем Модуль.алг (для вызова снаружи через точку) и под коротким именем алг (для вызова внутри). Тело модуля (глобальные объявления) исполняется сразу.

Экспорт из именованного модуля пока не действует Поле exports у Stmt::ModuleDecl заполняется пустым списком, а execute_export — это заглушка (TODO), не меняющая видимость. Значит, у модуль … кон все алгоритмы публичны, а экспорт в этом контексте не ограничивает набор. Целевое поведение: экспорт внутри модуля сужает публичный набор так же, как в файловом модуле. 📋

7.3 Разрешение главного файла

main_file_path(): если main — абсолютный путь, он берётся как есть; иначе присоединяется к корню проекта (каталогу манифеста). Именно этот путь использует резолвер импорта директории-проекта (раздел 3.2), с запасными расположениями, если файл не найден.

7.4 Прочие секции

Модель конфигурации предусматривает [dependencies] / [зависимости] (версия, path, git, registry, features), [dev-dependencies], [build-dependencies], [workspace] / [рабочее_пространство], [registries], [env], а также lock-файл (LockFile). Эти поля разбираются манифестом, но резолюция зависимостей, реестры пакетов и workspaces как механизм разрешения импортов ещё не задействованы резолвером (раздел 3 работает только с локальными путями и встроенными библиотеками). 📋 Управление пакетами — предмет будущего KITE и KITE 5 §10. 

[project]
name = "моя_библиотека"
version = "1.0.0"
authors = ["Ученик"]

[build]

8. Кэш, циклы и инициализация

  • Кэш модулей. FileImporter кэширует загруженные файлы по абсолютному пути. Повторный импорт того же файла возвращает уже загруженный модуль — файл парсится один раз. ✅
  • Обнаружение циклов. Импортер ведёт стек импортов; если файл уже в стеке, возвращается ошибка «Циклический импорт: <путь>». Циклические зависимости между файловыми модулями запрещены и диагностируются. ✅
  • Инициализация модуля. При загрузке файлового модуля из него собираются только алгоритмы (включая первую реализацию перегруженных) и классы. Глобальный код верхнего уровня файла не исполняется при импорте (поле globals заполняется пустым — TODO в коде). Поэтому глобальные переменные и побочные эффекты импортируемого файла недоступны. 📋
Библиотеки vs файловые модули — разные менеджеры Файловые модули обслуживает FileImporter (кэш, циклы, base-dir), а библиотеки — LibraryManager (реестр, версии, алиасы функций, выгрузка). Обнаружение циклов относится к FileImporter; у библиотек циклов по построению нет.

9. Ограничения и открытые вопросы

ОграничениеСтатус
Оператор Модуль::член исполняется наравне с точечной записью Модуль.член (обе формы разрешаются в одно полное имя).✅
экспорт внутри модуль … кон не ограничивает видимость (заглушка execute_export).📋
Глобальный код и переменные импортируемого файла не инициализируются (globals пуст).📋
Перегруженные алгоритмы модуля импортируются только первой реализацией.🧪
[dependencies], реестры, workspaces, lock-файл разбираются, но не участвуют в резолюции импортов.📋
Пространство имён на классы навешивается неоднородно (зависит от пути импорта); нужна унификация двух процедур регистрации.🧪
Импорт без алиаса «вливает» короткие имена в текущее пространство — возможны коллизии имён между модулями (арбитраж не специфицирован).🧪
Циклы между файловыми модулями запрещены и диагностируются (не разрешаются частично, как в некоторых языках).✅
Целевое направление Норматив на будущее: (1) ✅ реализовать ModuleAccess — сделано, :: равноправен точке; (2) сделать экспорт действующим и в именованных модулях; (3) исполнять инициализацию модуля предсказуемо; (4) унифицировать регистрацию имён (одна процедура вместо двух); (5) определить правило разрешения коллизий при импорте без алиаса.
